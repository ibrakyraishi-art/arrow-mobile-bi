## Контекст

Факт лежит в трёх видах источников: в ClickHouse (SQL), в файлах CSV/Excel/Google Таблицах и в демо (оба последних считаются in-JS). План вводится руками по месяцам и хранится в Supabase. Баер должен выбирать плановые значения в конструкторе как обычные поля (G10).

## Решение

На каждое поле плана к датасету добавляются пять виртуальных метрик: `<подпись> · план`, `· план на дату`, `· выполнение %`, `· прогноз`, `· отклонение`. Клиент передаёт в `/api/query` контекст `plan`. Сервер убирает виртуальные колонки из SQL и in-JS агрегации, сам добавляет исходную метрику, если её нет, получает даты каждой группы и дозаполняет колонки чистыми функциями модуля `plan`. Для ClickHouse даты берутся вторичным запросом `GROUP BY dims, date`.

## Почему

- **Отдельная таблица фактов** (факт копируется в Supabase рядом с планом и они джойнятся). Отвергнута, потому что это вторая копия факта. Её надо синхронизировать с каждым источником, и она отстаёт от живого ClickHouse. Графики на ней были бы отдельной сущностью, а не полями датасета.
- **Джойн плана внутри SQL источника.** Работает только для ClickHouse: план живёт в Supabase, а у CSV, Excel и демо SQL нет совсем. Пришлось бы держать два разных механизма.
- **Отдельный виджет «план/факт» вне конструктора.** Не выполняет G10: план не выбирается в сводной, комбо и метрике наравне с остальными полями.
- У выбранного варианта один движок на все три вида источников, а формулы и вычисляемые поля остаются как есть.

## Последствия

- В каждом запросе к датасету с план-проектом клиент передаёт поля и значения плана. Запрос становится толще, и сервер верит тому, что прислал клиент.
- Для ClickHouse на каждый такой запрос уходит лишний запрос дат, это плюс задержка.
- Виртуальные колонки не существуют ни в SQL, ни в схеме датасета. Их нельзя использовать внутри вычисляемых полей и фильтров движка, если это не доделать отдельно.
- Имя колонки строится из подписи поля плана. Если переименовать подпись, имя поменяется, и сохранённые графики потеряют ссылку на поле, если код не переносит ссылки.
- Логика `/api/query` усложняется: появляется шаг пост-обработки, который должен совпадать для in-JS и SQL путей.
